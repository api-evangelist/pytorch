<h2><b>How It Started: Hitting the GIL Wall at Scale</b></h2>
<p><span style="font-weight: 400;">We&#8217;ve been running production model serving for many years. When we first started building Shepherd Model Gateway, the goal was modest: figure out if cache-aware load balancing could improve routing across inference replicas.</span></p>
<p><span style="font-weight: 400;">It could. And as we went deeper, we found a much bigger problem.</span></p>
<p><span style="font-weight: 400;">In both SGLang and vLLM, tokenization and detokenization had become bottlenecks. Not in theory — in production, under real traffic. The root cause was architectural: although both engines use Rust or C++ tokenizer libraries underneath, the calls go through Python. That means the GIL. That means a single-threaded ceiling on CPU-bound work that sits directly in the serving path.</span></p>
<p><span style="font-weight: 400;">At a small scale, this doesn’t matter. At large-scale prefill-decode disaggregated serving, and at large-scale expert parallelism across GPU clusters, it matters enormously. These configurations make GPUs extremely fast — fast enough that the CPU side of the pipeline becomes the constraint. Every microsecond of GIL-bound tokenization is a microsecond where GPUs worth hundreds of thousands of dollars sit idle, waiting for input.</span></p>
<p><span style="font-weight: 400;">That’s where the journey really started. Not with a gateway vision — with a production problem. Could we disaggregate the entire CPU workload from the GPU path and run it in Rust? Not Python-calling-Rust. Pure Rust. No GIL. No single-threaded ceiling. No Python process boundaries.</span></p>
<p><span style="font-weight: 400;">The answer was yes, and the project that proved it became Shepherd Model Gateway.</span></p>
<p><a href="https://pytorch.org/wp-content/uploads/2026/04/architecture-animated.svg"><img alt="" class="alignnone size-full wp-image-76096" src="https://pytorch.org/wp-content/uploads/2026/04/architecture-animated.svg" /></a></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">SMG Architecture: Clients → Gateway → Router → Workers</span></em></p>
<p><span style="font-weight: 400;">SMG’s architecture is built on one principle: </span><b>GPUs should do tensor math. Everything else belongs in a dedicated serving layer.</b></p>
<p><span style="font-weight: 400;">We looked at the model-serving stack and identified every CPU-bound workload entangled with GPU inference: tokenization, detokenization, reasoning output parsing, function call extraction, MCP tool orchestration, multimodal preprocessing, chat history management, structured output validation, stop sequence detection. Each one is a CPU task that, when co-located with the GPU process behind the Python GIL, creates back-pressure on the most expensive hardware in the rack.</span></p>
<p><span style="font-weight: 400;">SMG moves all of these into a Rust gateway layer that communicates with inference engines over gRPC. The protocol is minimal and GPU-focused: send preprocessed tokens in, stream generated tokens out. Everything else is the gateway’s responsibility.</span></p>
<p><span style="font-weight: 400;">This isn’t the approach most projects in the distributed inference space have taken. Excellent work is happening with projects like NVIDIA Dynamo and llm-d, which focus on optimizing the inference engine layer and the orchestration around it. We see that work as complementary. But SMG’s bet is different: rather than making the engine smarter, make the gateway smarter. Offload everything that doesn’t require a GPU onto a purpose-built Rust layer that scales independently, evolves independently, and runs with zero GIL contention.</span></p>
<h2><b>The gRPC Re-Architecture: Making It Real</b></h2>
<p style="text-align: center;"><i><span style="font-weight: 400;"><a href="https://pytorch.org/wp-content/uploads/2026/04/2.svg"><img alt="" class="alignnone size-full wp-image-76103" src="https://pytorch.org/wp-content/uploads/2026/04/2.svg" /></a></span></i><em><span style="font-weight: 400;">The gRPC Pipeline: Gateway-side processing before engine handoff</span></em></p>
<p><span style="font-weight: 400;">The single largest technical investment in SMG’s history was rebuilding the entire serving pipeline around a native Rust gRPC data plane. This was the architectural proof of the disaggregation thesis.</span></p>
<p><b>Tokenization and detokenization </b><span style="font-weight: 400;">move into the gateway. SMG runs tokenizers natively in Rust with a two-level cache — L0 exact-match for repeated prompts, L1 prefix-aware at special-token boundaries. The inference engine receives pre-tokenized input and never touches a tokenizer. No Python. No GIL.</span></p>
<p><b>Reasoning and tool call parsing </b><span style="font-weight: 400;">runs in the gateway’s streaming pipeline. As tokens arrive over gRPC, SMG’s parsers — including Cohere Command, DeepSeek, Llama, Nemotron, Kimi-K2, GLM-4, and Qwen Coder — extract reasoning blocks, function calls, and structured output in real-time. No post-processing step on the engine side.</span></p>
<p><b>Multimodal processing </b><span style="font-weight: 400;">was the most ambitious piece. We rewrote major components of Hugging Face’s transformers image processor from Python to Rust — reimplementing vision preprocessing pipelines, tensor operations, and model-specific transformations in a completely different language and runtime. The result: SMG communicates preprocessed tensors directly to engines via gRPC with zero Python overhead. Support for Llama 4 Vision, Qwen VL, and all major vision-language models, with backend-specific optimizations for SGLang, vLLM, and TensorRT-LLM. This is, to our knowledge, an industry first.</span></p>
<p><b>MCP tool orchestration </b><span style="font-weight: 400;">runs entirely in the gateway with auth-aware connection pooling, concurrent batch execution, approval workflows, automatic reconnection, and HTTP header forwarding. The inference engine has no knowledge of MCP. We also built a complete built-in tool routing infrastructure — turning any MCP server into native capabilities (FileSearch, WebSearch, CodeInterpreter) for any model. Deploy Llama or Qwen with the same built-in tools as GPT-4.</span></p>
<p><b>Chat history management </b><span style="font-weight: 400;">with pluggable storage (PostgreSQL, OracleDB, Redis and in-memory), schema versioning via Flyway, customizable table/column names, and storage hooks for pre/post persistence callbacks. All in the gateway, keeping the engine stateless.</span></p>
<p><b>WASM middleware </b><span style="font-weight: 400;">provides programmable extensibility without forking the codebase. Custom authentication, compliance logging, PII redaction, cost tracking, compression — all via WebAssembly plugins with sandboxed isolation. Another industry first.</span></p>
<p><span style="font-weight: 400;">The gRPC protocol itself — published as smg-grpc-proto on PyPI — defines the narrow contract between gateway and engine. This design means you can upgrade your gateway (new parsers, new protocols, new tools) without touching your inference engine, and upgrade your engine (new GPU kernels, new quantization) without touching your gateway. They evolve independently because the interface is clean.</span></p>
<h2><b>What SMG Delivers Today</b></h2>
<p><a href="https://github.com/lightseekorg/smg"><span style="font-weight: 400;">SMG</span></a><span style="font-weight: 400;"> was created by Simo Lin and Chang Su, members of the LightSeek Foundation. In roughly six months, we shipped thirteen releases. Rather than walk through each one, here is what the project delivers today — and the evidence behind each capability.</span></p>
<h3><b>Multi-Model Inference Gateway</b></h3>
<p><span style="font-weight: 400;">A single SMG process fronts your entire fleet — multiple models, multiple engines, one entry point. Route requests across SGLang, vLLM, TensorRT-LLM, and MLX backends simultaneously. Add OpenAI, Anthropic, Google Gemini, AWS Bedrock, and Azure OpenAI as external providers. One gateway, every engine, every vendor.</span></p>
<h3><b>Five Native Agentic APIs</b></h3>
<p><span style="font-weight: 400;">SMG natively supports Chat Completions (OpenAI), Responses API (OpenAI), Messages API (Anthropic), Interactions API (Gemini), and Realtime API (WebSocket/WebRTC). These are not translation layers — each is a first-class implementation. The Messages API preserves thinking blocks end-to-end with ThinkingConfig, thinking_delta streaming events, and interleaved reasoning + text + tool use content blocks. The Responses API brings OpenAI&#8217;s conversation management to Llama, DeepSeek, Qwen, and every open-source model — SMG remains the only open-source gateway supporting it. Run agentic workflows designed for Claude on Llama 4, Qwen 3, DeepSeek, or Kimi with full protocol fidelity.</span></p>
<h3><b>Native Rust gRPC Data Plane</b></h3>
<p style="text-align: center;"><i><span style="font-weight: 400;"><a href="https://pytorch.org/wp-content/uploads/2026/04/tokenization-cache.svg"><img alt="" class="alignnone size-full wp-image-76106" src="https://pytorch.org/wp-content/uploads/2026/04/tokenization-cache.svg" /></a></span></i><em><span style="font-weight: 400;">Two-Level Tokenizer Cache: L0 exact-match, L1 prefix-aware</span></em></p>
<p><span style="font-weight: 400;">The architectural core: a native Rust gRPC pipeline between gateway and engine. The contract is minimal — preprocessed tokens in, generated tokens out. Everything else is the gateway&#8217;s responsibility. Tokenization runs in Rust with a two-level cache (L0 exact-match, L1 prefix-aware). Reasoning and tool call parsing runs in the streaming pipeline as tokens arrive — supporting fifteen model families including DeepSeek-R1, Qwen3, GLM-4, Kimi, Llama-4, Cohere Command, and more. No Python. No GIL. The gRPC protocol is published as smg-grpc-proto on PyPI, and both vLLM (</span><a href="https://github.com/vllm-project/vllm/pull/36169"><span style="font-weight: 400;">PR #36169</span></a><span style="font-weight: 400;">) and NVIDIA TensorRT-LLM (five merged PRs) have adopted it upstream.</span></p>
<h3><b>Intelligent Routing</b></h3>
<p><a href="https://pytorch.org/wp-content/uploads/2026/04/4.svg"><img alt="" class="alignnone size-full wp-image-76107" src="https://pytorch.org/wp-content/uploads/2026/04/4.svg" /></a></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">Cache-Aware Routing Flow</span></em></p>
<p><span style="font-weight: 400;">Eight load-balancing policies: cache-aware, round robin, random, power-of-two, consistent hashing, prefix hash, manual (sticky sessions), and bucket-based. Cache-aware routing was rewritten from the ground up — 10–12x faster (216,000 insertions/sec), 99% memory reduction (180 KB → 1.4 KB per node, 10,000 cached prefixes: 1.8 GB → 14 MB). Event-driven KV cache routing streams real-time cache state from all backends via SubscribeKvEvents RPC, with auto-learned block sizes. Production results on 8 Llama replicas: TTFT average down 23%, TTFT p99 down 28%. Prefill-decode disaggregation routes prefill and decode phases to separate worker pools with independent policies — 20–30% TTFT improvement in PD setups.</span></p>
<h3><b>Multimodal Processing in Rust</b></h3>
<p><span style="font-weight: 400;">We rewrote major components of Hugging Face&#8217;s image processors from Python to Rust — vision preprocessing pipelines, tensor operations, and model-specific transformations in a completely different language and runtime. Eight vision model families supported: Kimi K2.5, Llama-4 Vision, LLaVA, Phi-3/Phi-4 Vision, Pixtral, Qwen-VL, Qwen2-VL, and Qwen3-VL. Preprocessed tensors flow directly to engines via gRPC with zero Python overhead. To our knowledge, an industry first.</span></p>
<h3><b>MCP Tool Orchestration &amp; Built-in Tools</b></h3>
<p><a href="https://pytorch.org/wp-content/uploads/2026/04/mcp-architecture.svg"><img alt="" class="alignnone size-full wp-image-76110" src="https://pytorch.org/wp-content/uploads/2026/04/mcp-architecture.svg" /></a></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">MCP Architecture: Tool orchestration in the gateway</span></em></p>
<p><span style="font-weight: 400;">MCP runs entirely in the gateway with auth-aware connection pooling, concurrent batch execution, approval workflows, automatic reconnection, and four transports (STDIO, HTTP, SSE, Streamable). Universal MCP Built-in Tools turn any MCP server into native capabilities — FileSearch, WebSearch, CodeInterpreter — for any model. Deploy Llama or Qwen with the same built-in tools as GPT-4. Per-tenant isolation, policy-based trust levels, and execution metrics come standard.</span></p>
<h3><b>WASM Middleware</b></h3>
<p><a href="https://pytorch.org/wp-content/uploads/2026/04/wasm-plugins.svg"><img alt="" class="alignnone size-full wp-image-76117" src="https://pytorch.org/wp-content/uploads/2026/04/wasm-plugins.svg" /></a></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">WASM Plugin Pipeline</span></em></p>
<p><span style="font-weight: 400;">Programmable extensibility via WebAssembly plugins with sandboxed isolation — another industry first. Custom authentication, compliance logging, PII redaction, cost tracking, compression — all without forking the codebase. Built on Wasmtime with Component Model and async support. Storage hooks intercept chat history operations for custom pre/post processing.</span></p>
<h3><b>Enterprise Security &amp; Observability</b></h3>
<p><a href="https://pytorch.org/wp-content/uploads/2026/04/tls-architecture.svg"><img alt="" class="alignnone size-full wp-image-76118" src="https://pytorch.org/wp-content/uploads/2026/04/tls-architecture.svg" /></a></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">TLS/mTLS Architecture</span></em></p>
<p><span style="font-weight: 400;">JWT/OIDC authentication with JWKS discovery, role-based access control, API key auth, and multi-tenant rate limiting. TLS and mTLS for both client-facing and inter-node communication. A six-layer metrics system with 40+ Prometheus metrics covering HTTP, router, worker, inference, discovery, MCP, database, and mesh layers. Full OpenTelemetry distributed tracing. Structured JSON logging with request correlation.</span></p>
<h3><b>Reliability &amp; High Availability</b></h3>
<p><img alt="" class="aligncenter wp-image-76119 size-full" height="595" src="https://pytorch.org/wp-content/uploads/2026/04/closed.png" width="1400" /></p>
<p style="text-align: center;"><em><span style="font-weight: 400;">Circuit Breaker State Machine</span></em></p>
<p><span style="font-weight: 400;">Per-worker circuit breakers (closed/open/half-open), automatic retries with exponential backoff and jitter, periodic health checks, concurrent request rate limiting, request timeouts, and configurable graceful shutdown. SWIM-protocol gossip mesh with CRDT-based state sync for multi-node deployments. Distributed rate limiting via consistent hashing across cluster nodes. Partition-tolerant by design.</span></p>

Kubernetes label-based pod discovery, DNS discovery, or manual worker URLs. Model ID sourced from pod namespace, labels, or annotations. <h2><b>Proving the Thesis: gRPC Gateway Benchmarks</b></h2>
<p><span style="font-weight: 400;">The disaggregation thesis predicts that moving CPU workloads off the GPU path should show measurable benefits — especially under production conditions. We tested this systematically.</span></p>
<h3><b>Methodology</b></h3>
<p><span style="font-weight: 400;">All benchmarks run on NVIDIA H100 GPUs using NVIDIA GenAI-Perf (genai-perf) via the SMG nightly benchmark suite on GitHub Actions. 8 models (GPT-OSS-20B, Llama-3.1-8B, Llama-3.3-70B, Llama-3.3-70B-FP8, Llama-4-Maverick, Llama-4-Scout, Qwen2.5-7B, Qwen3-30B-MoE), 2 runtimes (SGLang, vLLM), 5 traffic scenarios, 9 concurrency levels (1–256). Total: 1,082 matched gRPC vs HTTP comparison points.</span></p>
<h3><b>The Scaling Story: Advantage Grows with Concurrency</b></h3>
<p><span style="font-weight: 400;">At concurrency 1, gRPC and HTTP perform within noise. At concurrency 256, gRPC delivers ~8% more throughput. The gateway’s binary serialization and HTTP/2 multiplexing compound under load — exactly when it matters.</span></p>
<p><img alt="" class="aligncenter wp-image-76125 size-full" height="1026" src="https://pytorch.org/wp-content/uploads/2026/04/smg-blog.png" width="1776" /></p>
<h3><b>Long Contexts: Where gRPC Transforms Performance</b></h3>
<p><span style="font-weight: 400;">HTTP/JSON serialization cost grows linearly with prompt length. gRPC/protobuf uses compact binary encoding that doesn’t pay this tax. At 7800 input tokens, the serialization cost is substantial. The D(7800,200) scenario shows +12.2% throughput advantage across all models.</span></p>
<p><span style="font-weight: 400;">The most dramatic result: Llama-3.3-70B-FP8 with 7800-token inputs. This model, running FP8 quantization on H100, is fast enough that HTTP serialization becomes the dominant bottleneck. gRPC delivers up to 3.5x higher output throughput: 1,150 tok/s vs 327 tok/s.</span></p>
<p><img alt="" class="aligncenter wp-image-76126 size-full" height="1026" src="https://pytorch.org/wp-content/uploads/2026/04/long-context.png" width="1775" /></p>
<p><img alt="" class="aligncenter wp-image-76129 size-full" height="1524" src="https://pytorch.org/wp-content/uploads/2026/04/blog.png" width="2048" /></p>
<h3><b>Per-Model Breakdown at High Concurrency</b></h3>
<p><span style="font-weight: 400;">At production concurrency levels (32–256), the gRPC advantage varies by model architecture. Llama-3.3-70B-FP8 sees the largest gains (+15.8% E2E p99, +44.6% output throughput). Smaller dense models (Llama-3.1-8B, Qwen2.5-7B) show modest improvements. The pattern is clear: faster GPUs → larger gRPC advantage, because CPU overhead becomes a bigger fraction of total latency.</span></p>
<p><img alt="" class="aligncenter wp-image-76130 size-full" height="645" src="https://pytorch.org/wp-content/uploads/2026/04/blog-formal.png" width="2048" /></p>
<h2><b>The Landscape</b></h2>
<p><span style="font-weight: 400;">We’re not the only team working on LLM infrastructure.</span></p>
<p><span style="font-weight: 400;">NVIDIA Dynamo brings deep hardware integration and optimized inference orchestration. llm-d tackles distributed inference scheduling with a Kubernetes-native approach. Both are doing important work at the engine and cluster layer.</span></p>
<p><span style="font-weight: 400;">SMG operates at a different boundary: the serving and protocol layer. We own everything between the client and the GPU — tokenization, agentic protocol translation, tool orchestration, cache-aware routing, multimodal preprocessing, reliability. One layer, zero external dependencies, pure Rust.</span></p>
<p><span style="font-weight: 400;">The key insight: these approaches compose. You can run SMG in front of vLLM managed by llm-d, or in front of TensorRT-LLM with Dynamo handling GPU orchestration. The boundaries are clean because the responsibilities are different.</span></p>
